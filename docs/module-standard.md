# Стандарт модуля (Задача 2)

> Единый контракт для всех нод графа исполнения. Базовая реализация —
> `project/core/base_module.py`, объект данных — `project/core/data_object.py`.

## 1. Куда класть модуль

- Каждая нода = папка с именем, совпадающим с именем модуля:
  `project/<имя_ноды>/<имя_ноды>.py`.
- В файле ровно один класс, наследующий `BaseModule`, с осмысленным snake_case
  именем: `CollectSources` в папке `collect_sources` (правило 2).
- Запрещённые имена: `utils`, `helpers`, `misc`, `common`, `temp`,
  `node_1`, `module_a` и т.п. (правило 3). Проверка зашита в
  `BaseModule.__init_subclass__` и срабатывает при импорте.
- Внутри ноды запрещено создавать вложенные ноды и подграфы (правило 5
  в первоначальной редакции): один класс = один шаг работы. **Пересмотр
  (лекция 5:36–11:00): подграф как сущность графа вводится** — длинная линейная
  цепочка сворачивается в узел-подграф («умение»), который запускается отдельно
  и работает так же; умения регистрируются в `docs/skills-registry.md`.
  Запрет остаётся про *вложенные* подграфы внутри одного класса ноды.

## 2. Базовый контракт `BaseModule` (правило 4)

| Свойство | Что обязана обеспечивать нода | API |
|---|---|---|
| **Killable** | Штатная остановка кооперативно: нода сама выходит между квантами, внешний вызов `request_stop_all()` доходит до всех работающих модулей | `request_stop(reason)`, `should_stop()`, `_check_stop()` (бросает `ModuleStopped`) |
| **HardKillable** (лекция 3:45) | Жёсткая останавливаемость: кооперативная остановка — не гарантия («обычный kill может не сработать — большая фантазия у нейронов»). Гарантия — изоляция ноды в отдельном процессе ОС, который можно убить SIGKILL'ом «на глухо». Нода обязана исполняться изолированно: без зависимости от глобального состояния интерпретатора | `core/process_runner.py`: `NodeProcess(name).start(data)` → `join()` / `hard_kill()`; демонстрация — `python3 project/run_node.py <нода> --kill-after 0.2` |
| **Throttleable** | Работает квантами; между квантами можно замедляться (ограничение CPU/частоты обращений к API) | `pace()` — вызвать минимум один раз за шаг; пауза задаётся `throttle_delay_seconds` |
| **Observable** | Отчитывается о прогрессе для статус-бара и оркестрации | `observe(step, message)`, `progress() → Progress` (статус, шаг, elapsed, ETA) |
| **Predictable** (лекция 4:44) | Предсказуемость: по поданным на модуль данным время работы от начала до конца оценивается **точно** — «на каждый модуль можно поставить progress bar, и он будет показывать точное время». Оценка до запуска (`predict`) обязательна для тяжёлых нод; `progress().eta_seconds` — вспомогательный, работает уже после старта | `predict(data) → float` (секунды; базовая оценка по объёму входа и `total_steps`) |
| **Semantically identifiable + отличимость** | Осмысленное имя и описание; имя = имя папки, нода сама объясняет своё назначение. **Отличимость (встреча №3, A1)**: один модуль = одна бизнес-функция; описание — **различимое идентифицирующее**: имя + назначение, по которым система (и нейронка) однозначно отличает модуль от любого другого. Дубли описаний запрещены | `name`, `description` (ClassVar, проверяются при создании класса; описание ≥ 30 символов — каскад в `core/guards.py`; различимость описаний — страж отличимости `DistinctnessGuard`, дубли бракуются как «модуль неразличим») |

Точка входа ноды в графе — `run(data)`:

```python
class ChunkText(BaseModule):
    name = "chunk_text"
    description = "Режет документы на чанки по пунктам ГОСТ и добавляет метаданные."
    total_steps = 2
    throttle_delay_seconds = 0.0

    def execute(self, data: DataObject) -> DataObject:
        self.observe(1, "нарезка документа 1/1")
        self.pace()                      # killable-квант
        # ... бизнес-логика (в этом проходе — заглушка) ...
        self.observe(2, "чанки готовы")
        return data                      # контракт: возвращает объект данных
```

`run()` оборачивает `execute()`: ставит статус `running`, фиксирует
`trace`, при штатной остановке ставит `data.status = "stopped"` и поднимает
`ModuleStopped`, при сбое пишет ошибку в `data.errors`. Нода не меняет
этот каркас — только `execute()`.

## 3. Стандарт объекта данных `DataObject`

Один объект передаётся по всему графу (StateGraph LangGraph). Каждое
**информационное поле заполняет строго одна нода** (правило 6): имя ноды —
префикс имени поля, коллизий нет.

| Поле | Тип | Заполняет | Смысл |
|---|---|---|---|
| `mode` | str | `user_interface` | маршрут прогона: `check` / `index` / `refresh` |
| `request` | str | `user_interface` | запрос пользователя (PDF решения + целевые ГОСТы) |
| `source_files` | list[str] | `collect_sources` / `refresh_corpus` | файлы корпуса для индексации |
| `documents` | list[dict] | `parse_document` | распарсенные документы (текст, таблицы, страницы) |
| `chunks` | list[dict] | `chunk_text` | чанки с метаданными (№ ГОСТа, пункт, раздел) |
| `vectors` | list[list[float]] | `embed_chunks` | эмбеддинги чанков |
| `embedder_cuts` | list[dict] | `embed_chunks` | входные ворота (B1): какие чанки разрезаны под лимит входа эмбеддера (обратная связь к чанкеру) |
| `stored_count` | int | `store_vectors` | сколько векторов записано в SQL-БД |
| `facts` | list[dict] | `extract_facts` | факты из чанков ГОСТа (числа, ограничения, утверждения) |
| `facts_stored` | int | `store_facts` | сколько фактов записано в графовую базу знаний |
| `candidate_requirements` | list[dict] | `retrieve_fragments` | top-K кандидатов из векторной БД |
| `literal_hits` | list[dict] | `literal_search` | дословные совпадения текста и чисел |
| `graph_candidates` | list[dict] | `graph_search` | связанные факты/пункты из базы знаний |
| `selected_requirements` | list[dict] | `rerank_fragments` | объединение трёх каналов + реранкинг |
| `context_pairs` | list[dict] | `build_context` | пары «пункт ГОСТ + фрагмент решения» |
| `tasks` | list[dict] | `distribute_tasks` | задачи для агентов (1 пункт = 1 задача) |
| `raw_answers` | list[dict] | `verify_requirement` | ответы LLM-агентов |
| `verdicts` | list[dict] | `format_verdict` | вердикты по схеме (статус/цитата/исправление) |
| `summary_verdict` | dict | `aggregate_verdicts` | сводный статус документа |
| `report` | dict | `compose_report` | итоговый отчёт |
| `presentation` | dict | `render_report` | подготовленный к показу отчёт |
| `followup_question` | str | `handle_followup` (инициирует `user_interface`) | уточнение пользователя |
| `metrics` | dict | `measure_quality` | метрики качества прогона |
| `capabilities_report` | dict | `system_self_awareness` | ответ системы самознания (маршрут `status`, см. `docs/node-map.md`) |
| `trace` | list[str] | `BaseModule.run()` каждой ноды | путь прогона: имена нод по порядку |
| `status` | str | `BaseModule.run()` | `idle / running / finished / stopped / failed / rejected` |
| `errors` | list[str] | `BaseModule.run()` (и ноды могут дополнять) | ошибки прогона |

## 4. Порты: единообразие стыковки (лекция 4:22)

Ноды стыкуются по портам: «если одна нода посылает другой текст — другая обязана
его съесть; если шлёт более сложный объект — обязана его принять». У нас порт =
информационное поле `DataObject`:

- **Тип порта зафиксирован** в `core/data_object.py::PORT_TYPES` (поле → тип).
  Нода не может изменить тип поля — потребители ниже по цепочке не «съедят»
  чужой тип. Проверка — `validate_port(name, value)`; вызывается нодами-владельцами
  перед записью.
- **Владелец порта** — нода, которая его заполняет (колонка «Заполняет»
  в таблице выше и в `docs/node-map.md`); правило 6: одно поле = одна нода.
- Входы/выходы каждой ноды по портам перечислены в `docs/node-map.md`.

## 5. Сборка графа и среда исполнения (конституция п.11)

- Граф собирается в `project/core/graph_builder.py`: все ноды импортируются
  по одному, каждая оборачивается `BaseModule.run`, добавляется в
  `StateGraph` с состоянием `DataObject` (правило 1). Типы портов проверяются
  `validate_port()`; сбор графа эмитит события `node_added` для стражей
  (`core/guards.py`, запуск по событиям, не по таймеру).
- **Всё исполняется в среде LangGraph** (встреча №3, A2): основной граф,
  умения-подграфы и одиночные ноды. Единая точка исполнения —
  `core/graph_runtime.py`: `invoke_main` (полный граф), `invoke_node`
  (одноузловой подграф START → нода → END), `invoke_skill` (умение).
  CLI-инструменты (`run_node.py`, `run_skill.py`, `run_skeleton.py`, смоуки,
  `run_tests.py`) — **поверх графа**, не вместо него: изоляция процесса
  (`core/process_runner.py`) жёстко останавливает процесс, но исполняется
  нода внутри него по подграфу LangGraph.
- Исполнение мимо графа исключено: прямой вызов `run()`/`execute()` перехватывает
  страж «ничего вне графа» (первый обязательный страж, `core/guards.py`) —
  событие `outside_execution` + жёсткий возврат в граф.
- Топология маршрутов check / index / refresh / status — в `docs/node-map.md`.
- Трёхуровневое тестирование (модуль → умение → целиком) — `docs/testing.md`,
  команда `python3 project/run_tests.py`; холостой прогон: `python3 project/run_skeleton.py`
  — прогоны в четырёх маршрутах должны проходить без ошибок; `trace` для
  маршрута `check` покрывает 18 нод основного конвейера проверки.
