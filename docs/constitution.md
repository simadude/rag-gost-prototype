# Конституция проекта (A2, A5)

> Задание лекции №2 (2:28–5:00): «сначала нужно ввести конституцию — набор базовых
> принципов, которые **нельзя нарушать**». Без неё нейронка перезапишет любой
> контракт, и модули переиспользовать будет нельзя — «всё придётся постоянно
> переписывать».
>
> Конституция — **высший** уровень правил. Технический раскрой контракта —
> `docs/module-standard.md`; расхождение правится в пользу конституции.

## 1. Быть по контракту

Главный принцип. Каждый модуль работает строго по единому контракту
(`docs/module-standard.md`): единый объект данных `DataObject`, единый базовый
класс `BaseModule`, единая структура «папка = модуль = нода». Без общего стандарта
модули не переиспользуются, и всё придётся постоянно переписывать. Модуль «не по
контракту» к графу не допускается.

## 2. Модуль — отдельный исполняемый пакет в папке узла

Каждая нода — отдельный исполняемый фрагмент кода (пакет) в отдельной папке,
названной именем узла: `project/<имя_ноды>/<имя_ноды>.py`. Узел порождает
фрагмент/пакет кода — это вторая техническая страховка от монолитной «колбасы»
(вместе с LangGraph). Принцип неизменяем: сколько бы нод ни стало — 24 или 700.

## 3. Жёсткая останавливаемость

Любой модуль обязан останавливаться **глухо**: кооперативный выход между квантами
(Killable) — только первая ступень; гарантией является изоляция модуля в
отдельном процессе, который можно убить средствами ОС (SIGKILL). «Не надейтесь,
что обычный kill сработает, — может не сработать по многим причинам, одна из них
— очень большая фантазия у нейронов». Основополагающее свойство для цепочек,
проходящих много кругов. Реализация: `core/process_runner.py` (изоляция +
гарантированное убийство), контракт — в `module-standard.md`.

## 4. Предсказуемость

По поданным на модуль данным время его работы от начала до конца оценивается
**точно**: «на каждый модуль можно поставить progress bar, и он будет показывать
точное время». Контракт: нода обязана уметь заранее оценить свою работу
(`BaseModule.predict(data)`), а не угадывать по ходу; текущий ETA — вспомогательный.

## 5. Единообразие портов

Ноды стыкуются по портам: «если одна нода посылает другой текст — другая обязана
его съесть; если шлёт более сложный объект — обязана его принять». Порт — поле
`DataObject` с зафиксированным типом и владельцем-нодой. Нода-получатель обязана
принимать тип порта, который шлёт нода-отправитель; типы портов фиксируются
таблицей портов в `module-standard.md` и проверяются при сборке графа.

## 6. Один объект данных и одно поле — одна нода

По графу исполнения ходит единственный `DataObject` (StateGraph LangGraph).
Каждое информационное поле заполняет строго одна нода — имя ноды является
префиксом имени поля.

## 7. Подграфы-умения и реестр умений

Любая длинная линейная цепочка («один линейный конвейер») сворачивается в один
узел-**подграф**: фрагмент цепочки, который можно запустить отдельно, и он будет
работать так же. Подграф как сущность графа — **умение**; каждое умение удобно
тестировать отдельно. Умения регистрируются в реестре: `docs/skills-registry.md`.
Подграфы *внутри ноды* по-прежнему запрещены (один класс = один шаг работы);
свернутый в узел фрагмент — это отдельная сущность графа, а не подграф внутри ноды.

## 8. Внешний контур и провайдеры

Всё тяжёлое, требующее отдельных условий, и то, что хочется спрятать/защитить,
выносится **за внешний контур** как службы-провайдеры. У нас за контуром:
SQL-БД векторов, база знаний, эмбеддер-служба, LM-провайдер (агенты). Доступ —
только через **правильные коннекторы**. Главный запрет той же природы:
**сквозь БД ничего не течёт** — в базу ходят и от неё получают ответы; база —
способ хранения, не труба. Замена любого провайдера (SQLite → PostgreSQL) должна
происходить «щелчком пальцев» — сменой коннектора, без правки нод.

## 9. Схема — Mermaid

Внутренний стандарт представления схемы — **Mermaid** (внутренний стандарт
LangGraph, они «дружат»; DAG LangGraph понимает очень даже здорово). Единственный
источник схемы — `docs/diagram.mmd`; любые картинки (matplotlib/pyvis) — только
производные и не источник. Это же правило делает схемы переиспользуемыми между
проектами: стандарт представления не привязан к нашим генераторам.

## 10. Защита — часть системы: стражи на графе, по событиям

Принципы конституции защищают **стражи** — специальные модули, живущие **на самом
графе** и запускающиеся **методом самого графа** по **событиям** изменения
состояния графа (нода добавилась / изменилась). Выносить защиту наружу — нельзя
(внедрённая в систему защита удаётся всегда, вынесенная — не всегда); таймеры —
запрещены («события хорошо, таймеры плохо»: таймаут — зло, на котором система
виснет). Стражей может быть много, каждый защищает одно отдельное свойство.

## 11. Всё исполняется в среде LangGraph (встреча №3, A2)

Основной граф, умения-подграфы, стражи и одиночные ноды — всё исполняется
**только в среде LangGraph**. «Обязательно нужно дожать до состояния LangGraph,
потому что иначе код расползётся»; «эту схему нельзя тестировать до того, как
всё попадёт в LangGraph, прям нельзя — код прорастёт друг в друга».

- Точки входа CLI (`run_node.py`, `run_skill.py`, `run_skeleton.py`, смоуки,
  `run_tests.py`) — **инструменты поверх графа**, а не вместо него.
- Изоляция процесса (`core/process_runner.py`) — средство жёсткой остановки
  (SIGKILL), не среда исполнения: внутри процесса нода исполняется
  одноузловым подграфом LangGraph (`core/graph_runtime.invoke_node`).
- Исполнение мимо графа перехватывается: прямой вызов `run()`/`execute()`
  у модуля ловит **страж «ничего вне графа»** (первый обязательный страж)
  и исполнение жёстко возвращается в граф.
- Правило тестирования: **тестировать схему — только после полной
  LangGraph-миграции**, иначе код «дефундирует» (прорастает друг в друга).
  Регламент — `docs/testing.md`.

## 12. Отличимость модулей (встреча №3, A1)

**Один модуль = одна бизнес-функция.** Система может отличить один модуль от
другого: у модуля есть **различимое идентифицирующее описание** — имя
(= имя папки = имя ноды) + назначение, по которому система (и нейронка)
однозначно различает модули. Это усиление «Semantically identifiable»
(`docs/module-standard.md`): мало «имя осмысленное и описание ≥ 30 символов» —
описание должно **выделять модуль среди всех остальных**. Дубли описаний
(даже в другом регистре/пробелах) бракует **страж отличимости**
(`core/guards.py::DistinctnessGuard`); неразличимые модули «сольются» —
и для системы, и для нейронки, которой модули предъявляются как реестр.
